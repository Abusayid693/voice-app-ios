# 14. EPUB import, alongside PDF rather than deeper PDF heuristics

**Status:** Accepted
**Date:** 2026-10-06

## Context

PDF structure extraction is an open-ended cost, not a closed one. A single pass over two real books produced eleven narrow, independent fixes to `PDFParagraphAssembler`/`PDFTextExtractor` — drop-cap leading, drop-cap indent, a `combining` left-edge comparison, a separator font-size bug, split-line merging, a font-size merge guard, duplicate-selection dropping, newline-inside-a-line normalization, multi-letter roman-numeral list markers, an empty-match roman-numeral regex, and list markers with no following space — each found only by dumping a real page's geometry and comparing it against the source image. The underlying cause is structural, not a backlog of one-off bugs: `PDFParagraphAssembler` infers paragraph boundaries, headings, and list items from a handful of geometry scalars (leading, indent, x-position, font size, a marker regex), and every bug found so far was a case where the real signal the document actually carried wasn't expressible in those scalars. Two separate hypotheses about column-interleaving causes were also wrong before the real one (a stray single-line fragment vetoing side-by-side column detection) was found by dumping the actual PDF rather than reasoning about PDFKit's behavior abstractly. There is no principled reason to believe the list of fixes is finite, and a decorative swash-capital title (`"Annie"` extracted as `"nnie A"`) was found to be theoretically recoverable but not safely so in production — a reordering pass that fixed one book's 23 titles produced 93 destructive rewrites in another.

The alternative is not "write better PDF heuristics." It's a different source format whose structure doesn't need to be inferred at all: EPUB's reading order is the OPF `<spine>`, its paragraphs are `<p>`, its headings are `<h1>`–`<h6>`, its quotes are `<blockquote>`, its lists are `<ol>`/`<li>`. None of the eleven PDF bugs above has an EPUB analogue, because none of their causes exist in EPUB: there's no ligature loss (real Unicode characters, not glyphs with an unreliable `ToUnicode` map), no drop-cap misreading (CSS, the text itself is untouched), no running heads to strip (a print-pagination artifact), no scrambled decorative title (no glyph-draw-order dependency).

## Decision

**Add EPUB import as a second format, not a replacement for PDF or for further PDF investment.** Users still import PDFs; EPUB is additive where available. `PDFImportManager` keeps its historical name and directory (`Application Support/PDFImports/`) — this repo already keeps historical names where a rename would orphan in-flight state for no functional gain (`Features/Chapters/`, `LibraryTabView`) — and gains a `BookImportFormat` discriminator (`PDFImportJob.format`, Optional so every job already in `jobs.json` decodes unchanged) that routes to either `PDFProcessingActor` or the new `EPUBProcessingActor`. Both expose the identical `process(job:progress:) -> PDFImportResult` contract, so the manager's retry/cancel/delete/resume machinery, shelf reservation, and progress plumbing — none of which ever touched PDFKit specifically — needed no change at all.

**No third-party dependency.** Verified against the iOS SDK before writing any parsing code: `Compression.framework`'s `COMPRESSION_ZLIB` algorithm decodes a ZIP entry's raw DEFLATE stream (RFC 1951, no zlib header/trailer) directly through `compression_decode_buffer` — confirmed empirically with a known raw-deflate buffer, since the framework's naming invites the opposite assumption. `Foundation.XMLParser` handles the XHTML, with one real gap: strict XML rejects the HTML named entities (`&nbsp;`, `&mdash;`, `&rsquo;`) that real EPUB prose uses constantly, which `EPUBXHTMLEntities` substitutes before parsing. `anydoc-swift`, evaluated and rejected, is a Rust bridge whose `Package.swift` hard-fails outside macOS/Linux — no iOS slice exists.

**Pages are chapter-wise by construction, not packed by word count alone.** `EPUBProcessingActor` resolves the table of contents to an ordered `[EPUBTOCEntry]` (title, content-document path, `#fragment`, nesting depth) rather than the `path -> title` dictionary a first pass produced, because that shape cannot preserve order, cannot hold more than one chapter per content document, and cannot carry depth — all three are real: books exist that put several chapters, or their entire text, in one XHTML file and tell them apart only by fragment. Each spine document is cut into sections at every TOC entry that resolves inside it, not just at the document's own boundary, and `PageSplitter.split(units:)` runs once per section rather than once for the whole book — which is what makes a chapter boundary always land on a fresh page rather than sharing one with the tail of the previous chapter. A TOC entry whose fragment doesn't resolve in its own document is dropped rather than failing the import.

**Reader-facing EPUB types stay out of the import pipeline's own model layer.** `EPUBChapter` (persisted, read by the reader) lives in `Features/Chapters/Models/`, not beside `EPUBBlock`/`EPUBTOCEntry` (import-time-only, never persisted) in `Features/Import/Models/` — the same direction `ReaderTextRect`'s own doc comment already established for PDF (`PDFNormalizedRect` stays in Import; the reader has no business depending on the import pipeline's models). `PageSplitter`'s EPUB-facing overload takes a generic `StyledUnit { text, style: ReaderTextStyle? }` rather than `EPUBBlock` directly, for the same reason.

## Consequences

**Scope is deliberately narrow for this pass.** Cover art only — no inline images. No table support (a document that is only a `<table>` contributes no blocks and no chapter, matching the PDF path's own lack of table support rather than a new gap). `EPUBBlockKind`'s quote/list/caption cases carry no visual distinction beyond their literal text, because `ReaderTextStyle` has no italic or indent axis to express them with; only headings get real scale/weight styling. List markers (`"1. "`, `"• "`) are synthesized by the parser since EPUB's DOM carries none — a renderer generates them from CSS — but only as plain decimal, with no `list-style-type` awareness.

**The Pages picker gained real hierarchy, not just labels.** Top-level chapters render as collapsible headers, collapsed by default with the current chapter auto-expanded, rather than a flat list with inline section headers — a first pass that was rejected before implementation because it didn't match the intended "tap a chapter to reveal its pages" interaction. Nested (depth > 0) TOC entries get no header of their own; their pages simply live inside their parent's expanded range. A PDF (no chapters) renders exactly as before — this is additive to that code path, not a redesign of it.

**`ReaderPage.currentFormatVersion` bumped (5 → 6)** because EPUB pagination changed after some EPUB jobs may have already run during development — the same resume-safety mechanism that protects PDF re-extraction across an app update applies identically here, since both formats share one counter.

**Validation mirrors the PDF path rather than inventing new conventions:** `META-INF/encryption.xml` present → rejected as DRM'd (the EPUB analogue of `isLocked`), no `<spine>` items → rejected, and the same ≥500-alphanumeric-character floor across the finished book. Archive- and package-level errors (`EPUBArchiveError`, `EPUBImportError`) are both `LocalizedError` and propagate with their specific message rather than being caught and collapsed into one generic failure.

**Verified without a real downloaded EPUB in the repo** — none was available — against synthetic fixtures covering one-chapter-per-file, several chapters sharing one file via fragments, an entire book in one file, a nested table of contents, a TOC entry pointing at a missing anchor, and the EPUB 2 NCX fallback, run through the actual production `EPUBArchive`/`EPUBPackageReader`/`EPUBContentParser`/`EPUBProcessingActor` sources (not replicas) in a macOS command-line harness — the pattern that caught bugs a replica-based harness hid during the PDF work this ADR's Context section describes. A real downloaded EPUB remains worth testing against before relying on this for an unusual book; synthetic fixtures cannot cover every producer's real-world quirks.
