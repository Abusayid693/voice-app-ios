# CLAUDE.md

Architecture guide for this repo. Read this before making structural changes to the iOS app at `local-tts/native-ios/`. For *why* things are the way they are, see `docs/adr/` (one file per decision) and `CHANGELOG.md` (what shipped, by version) — this file is the *how to organize new code* reference only.

**Keep the "Target file tree" section below in sync with reality.** Whenever the actual folder structure changes (a Feature added, a Core utility added, a layer introduced), update it in the same commit.

## Project

Standalone native iOS SwiftUI app — no Expo/CocoaPods, so CoreML/FluidAudio integrate directly with no bridge layer — Xcode project generated by `xcodegen` from `local-tts/native-ios/project.yml`. Never hand-edit `KokoroAneTest.xcodeproj` — edit `project.yml` and run `xcodegen generate`.

xcodegen detail: `project.yml`'s `sources: [Sources]` is a whole-folder reference — xcodegen recurses automatically, so new subfolders under `Sources/` need **no** `project.yml` edit, only `xcodegen generate` re-run before building. Exception: `Info.plist`'s path is referenced explicitly via `info.path:` and must be updated if it moves.

**Before every commit that touches `Sources/`, `project.yml`, or adds a bundled resource folder**: run `xcodegen generate`, then check `DEVELOPMENT_TEAM` in the regenerated `KokoroAneTest.xcodeproj/project.pbxproj` still matches `project.yml`'s `DEVELOPMENT_TEAM` (`grep -n DEVELOPMENT_TEAM KokoroAneTest.xcodeproj/project.pbxproj`). Xcode's automatic signing has silently rewritten this to a different team mid-session more than once, and once leaked into a `main` merge — catching it before committing avoids shipping a stale/wrong signing team in the generated project file. A new SwiftPM package dependency is exactly as fragile if added by hand-editing `project.pbxproj` instead of `project.yml`'s `packages:`/target `dependencies:` — happened once with `Hugeicons` (below), and reproduced directly: regenerating from the `project.yml` as it stood on disk silently deleted the hand-added dependency, which would have broken the next person's build with no warning.

Three icon packages are in play right now, mid-migration, not a mistake to consolidate reflexively: SF Symbols (system look, including Library's local presentation controls), `LucideSwift` (this app's default non-system icon set, most call sites), and `Hugeicons` (`https://github.com/iSapozhnik/hugeicons-swift`, pinned by `revision:` — no tagged release as of this pin) — replacing Lucide in a growing but incomplete set of call sites (`ImportHomeView`, `ChapterPlayerView`'s play/pause). The visible tab bar is the exception: its four stable outline/filled pairs are original code-native paths in `TabNavigationIcon.swift`, so selection never swaps to an unrelated package glyph. Check which a given file already uses before adding a new icon to it rather than assuming; the archived Explore menu and most of `ChapterPlayerView` deliberately mix both.

## Architecture: MVVM + Services, feature-first folders

Views bind to a ViewModel; ViewModels own `@Published` UI state and orchestrate; Services own the actual async SDK/engine calls. Views never call an SDK directly; ViewModels never call `AVAudioPlayer`/FluidAudio directly.

- **View** — SwiftUI only, no business logic. `@ObservedObject`/`@StateObject var viewModel: ...`, bindings like `$viewModel.text`.
- **ViewModel** — `@MainActor final class ...: ObservableObject`. Owns `@Published` state, calls into Services, translates results into UI state. Never touches FluidAudio or AVFoundation types directly.
- **Service** — owns the actual async SDK calls (FluidAudio managers, `AVAudioPlayer`, HTTP calls). Reports progress via callback closures passed in by the ViewModel, not via its own `@Published` state — all `@Published` state lives on the ViewModel only.
- **Model** — plain data/enums, no logic.
- **Core/** — cross-feature utilities with no feature-specific meaning (e.g. a generic HTTP/JSON helper used by more than one feature's Service).
- **`DesignSystem/`** — cross-feature UI tokens: layout primitives (`WordFlowLayout`, `BlobShape`), shared sheet chrome (`StandardBottomSheet`, `ProgressiveHeaderBlur`), the shared type scale and spacing (`Typography.swift`, `Spacing.swift`), button chrome (`ButtonStyles.swift`), and the app's fixed color palette (`Colors.swift`). **`Shared/`** — not created yet; add only when a real second consumer exists, same as everything else here.

**One ObservableObject per concern — object granularity *is* re-render granularity.** `objectWillChange` carries no information about *which* property changed, so every `@Published` write re-renders every view observing that object. Two concrete bugs came from ignoring this while everything lived on `TTSViewModel`: the preview metering loop (~15 writes/sec) re-rendered the whole 70-tile voice grid for the length of every preview, and pack-download progress re-rendered every screen that merely reads pack readiness. Both were fixed by splitting the state onto its own object (`VoicePreviewPlayer`, `VoicePackStore`), not by memoizing views. Two rules follow: when adding state to a ViewModel, ask whether it changes at a different *rate* than what's already there — if so it wants its own object; and a view must not subscribe to an object it never reads. That second rule is now enforced structurally by `App/AppEnvironment.swift`: objects a view only hands onward arrive bundled in that one plain, non-observable container (held as an ordinary `let`, so it subscribes to nothing), while objects a view genuinely observes are passed to it explicitly as `@ObservedObject` parameters. Deliberately **not** `@EnvironmentObject`, which has no non-subscribing read and would re-render every view that merely touches an object — nor a custom `EnvironmentKey`, for the reason in that file's tree entry above. This also caught a real case: `LibraryTabView` was observing `TTSViewModel` only to forward it. Note nested `ObservableObject` changes do **not** reach a parent's `objectWillChange` — that's why views reach the store as `viewModel.packs` and observe it directly, rather than through a forwarding property on `TTSViewModel`.

**Voice metadata belongs in `VoiceCatalog`, nowhere else.** Anything describing a voice — user-facing alias, avatar, persona tagline, preview line, locale — goes on `Voice` and into that catalog. Raw engine codes remain the synthesis and persistence identity; `VoiceDisplayName` resolves a catalog alias at presentation time and only falls back to `VoiceCode`, so saved projects and historical Stats sessions never need migration when display copy changes. It used to live as five sparse dictionaries plus two divergent prefix parsers spread across a View file and a ViewModel, which meant adding one language touched six files and shipped a bug from a missed spot. Don't reintroduce a per-voice lookup table next to the code that consumes it; add a field to `Voice` instead. Same rule for the code-prefix convention (`af_`/`bf_`/`zf_`/`jf_`): `VoiceCode` is the only place that parses it.

Each row is built by `WordFlowLayout` (`DesignSystem/WordFlowLayout.swift`), not concatenated `Text` — per-word background highlighting needs each word to be its own styleable view, which `Text + Text` can't do; every word carries constant padding regardless of highlight state, and a paragraph's construction never changes based on playback state (only which word's background is filled) — the "construction must stay fixed" rule from an earlier pause/resume reflow bug. **Read-along scroll-jank fix**, the reason for most of the state here: precomputed `paragraphWordItems`/`paragraphRevisions` (one revision *per paragraph*, not a shared counter — a streaming chunk arrival changes exactly one paragraph's words) feed `ParagraphRow: View, Equatable`, whose `==` compares only scalars/small enums so SwiftUI can skip re-running a paragraph's `body` entirely when nothing changed — without this, `chapterPlayer`'s 4Hz ticker rebuilt every paragraph's full word list on every publish regardless. `recomputeWordItems` does the one O(words) comparison (`FlowWordItem: Equatable`) that decides which revisions to bump, once per chunk arrival, never inside `ParagraphRow.==` itself. **Revisions come from one monotonic counter (`revisionCounter`) and are never reset or reused** — since `==` deliberately doesn't compare `items`, a revision's only job is to differ from the value a row last rendered with, and per-row counters restarting at 0 (what a group-count change used to do) could hand a row the same revision alongside completely different content: `==` then reported equal, SwiftUI skipped the body, and the row rendered *stale* text until some unrelated compared field changed. Relatedly, a row is the **same view type whether or not it's the playing one**: `TimelineView` wraps every row (only the tick interval varies, 0.08s vs effectively never) rather than sitting inside an `if`, since an `if`/`else` between a wrapped and unwrapped row changes its structural identity, tearing it down and re-measuring it — and everything below it in the `LazyVStack` — each time the highlight entered or left. `groupHeightsBox`/`ScrollActivity` are reference-type boxes in `@State`, not `@State` values directly — mutating a class property doesn't invalidate the view the way reassigning a `@State` value does, which matters since tap-height measurement fires on every layout pass and drag events fire at display rate. **Auto-scroll** pauses on any manual scroll (`isAutoScrollPaused`), resumes only when the user taps the floating "jump to current word" pill, not a timer — `ReaderScrollVisibilityObserver` (`.onScrollVisibilityChange` on iOS 18+, `LazyVStack` onAppear/onDisappear as the iOS 17 fallback — the read-along uses `LazyVStack` specifically so that fallback's timing correlates with real scroll visibility) tracks which paragraph is on-screen so the pill only shows when the playing paragraph is genuinely scrolled off. A multi-chunk paragraph auto-scrolls to a progress-anchored point matching the playing chunk's own position within it, not always centered. Tap-to-seek estimates a target chunk from where within a merged paragraph the tap landed (character-length-weighted, via `SpatialTapGesture` + a `GeometryReader`-measured row height). **Floating player** collapses to a small pill (`isPlayerCollapsed`) or expands to the full transport bar, `matchedGeometryEffect`-animated between the two, Liquid Glass on iOS 26+ (tinted with the derived `ReaderChromeTheme`) or a matching two-mode material fallback below that. **PDF import (text-layer v1):** PDF import uses Apple's PDFKit entirely on-device; no third-party extractor, server upload, or OCR is involved. Embedded images are ignored for reading, while a small rendered image of physical page 1 becomes the optional project cover. A PDF whose distributed sample pages contain no selectable text is rejected with the scanned-PDF message. `PDFKitTextExtractor` reconstructs a best-effort reading order from line geometry rather than trusting `PDFPage.string`: it normalizes page rotation/crop coordinates, treats wide lines as bands, clusters the remaining lines by horizontal start to infer columns, and reverses column order for predominantly RTL text. This works for conventional single-/multi-column pages but tables, overlapping callouts, vertical writing, and unusual magazine layouts remain best effort.

PDF imports are page-preserving: every physical PDF page produces exactly one `ReaderPage` with the same zero-based index, and blank physical pages remain present as empty reader pages. Bookmarks, outlines, headings, and document word count never create or merge pages. Running heads and feet are removed by three rules, all confined to the top/bottom 12% band: a line whose normalized signature (lowercased, digit runs → `#`, whitespace collapsed) recurs in that band on **at least 3 pages**; a line that is entirely a page number (arabic or roman, optionally "Page N"); and a line carrying *this* page's own folio, where the folio's offset from the physical page index is itself detected as the dominant offset across ≥35% of pages. Three rules because heads differ per side of the spread — the verso usually carries the *book* title (identical document-wide) while the recto carries the *chapter* title, which covers only its own chapter, so a proportional threshold could never catch it and the folio is the only half of that head always recognisable. The recurrence bar is a count rather than a share for the same reason; what keeps a count that low safe is that the band already excludes body text, plus a size guard — a line larger than the document's body size is never collected as a head, and the same band + size conditions are re-checked when the collected signature is matched against a page, or a chapter's own opening title (same words, set large, mid-page) would be deleted along with its running head. A trailing hyphen is removed only before a lowercase continuation. V1 rejects locked PDFs, requires at least 500 extracted alphanumeric characters across the completed document, and has no manual-review step.

**Drop caps are a special case for paragraph assembly, because they break two of its four break rules at once.** A drop cap is several lines tall, so the line carrying it reports a top well above its own text: rule 2 (extra leading) measures from the previous line's top and fires on the overhang alone, and rule 4 (first-line indent) sees the cap's line start *at* the margin while the next line or two are inset *around* the cap — the exact shape of an indented first line. On one real page that split `"…to torture"` from `"humanity…"` mid-sentence (leading 29.4 against a 29.25 threshold; inset 14.7pt around the cap against that book's own 23.3pt paragraph indent). Both rules are now gated on `previousCarriesDropCap` (previous line taller than 2× body size). The same geometry also made `combining` glue `"I" + "am convinced"` into `"Iam convinced"` and `"…to torture" + "humanity"` into `"torturehumanity"`: its gap test compared left *edges*, which a tall cap sharing a row with two body lines satisfies at a hugely negative gap, and its word-space threshold was scaled off the *larger* of the two font sizes, putting the bar at 10.5pt where a real space measures 2.4pt.

**A decorative title set in swash capitals is extracted scrambled, and this pipeline cannot fix it.** One book's chapter title came back as `"nnie A"` — the PDF draws `nnie` first and the ornamental `A` last, `page.string` preserves that content-stream order, and `selectionsByLine()` collapses the whole title into one rect, so no per-letter geometry survives at the level this extractor works at. The positions *do* exist one level down, but only via `PDFPage.characterBounds(at:)`, which is indexed by **glyph, not character** despite its name and despite `numberOfCharacters == string.count` — every index after a PDFKit-inserted newline is shifted, and the mapping degrades further on ligature-dropping documents (a glyph with no character), where it was measured drifting by one mid-page. A reorder pass built on it fixed all 23 titles in that book but produced 93 destructive rewrites in another (`"Taxes"` → `"esTax"`), because a shift-by-one inside a line is a rotation of itself and so passes any same-characters check. Not attempted in production; if revisited, the discriminator that worked was a genuine backward jump in x while walking a line in string order, gated per *page* on most lines reconstructing exactly.

**EPUB import** removes this whole problem class rather than mitigating it, which is why it exists alongside the PDF path rather than as a replacement for more PDF heuristics: reading order is the OPF `<spine>`, paragraphs are `<p>`, headings are `<h1>`–`<h6>`, quotes are `<blockquote>`, lists are `<ol>`/`<li>` — no ligature loss (real Unicode, not glyphs), no drop-cap misreading, no running heads, no scrambled decorative titles. `EPUBArchive` → `EPUBPackageReader` → `EPUBContentParser` → `EPUBProcessingActor` (all under `Features/Import/Services/`, detailed in their own file-tree entries above) parse the container, resolve the table of contents to an ordered `[EPUBTOCEntry]`, parse each spine document into `[EPUBBlock]`, and page the result. **Pages are chapter-wise, not just word-count-packed**: a page always starts at a spine document boundary *and* at every TOC anchor that resolves inside one, so a book that puts several chapters — or its entire text — into one XHTML file (told apart only by `#fragment`) still pages as if each chapter had its own file, and two chapters never share a page. Cover art comes from the OPF's own declared cover image, not a rendered first page. No table support (a document that is only a `<table>` contributes no blocks and no chapter), and `EPUBBlockKind`'s quote/list/caption cases carry no visual distinction beyond their text (`ReaderTextStyle` has no italic or indent axis to express them with) — only headings get real `ReaderTextStyle` scale/weight. Validation mirrors the PDF path: `META-INF/encryption.xml` present → rejected as DRM'd (the EPUB analogue of `isLocked`), no `<spine>` items → rejected, and the same ≥500-alphanumeric-character floor across the finished book.

Imports are durable jobs under `Application Support/PDFImports/<job-id>` (the directory keeps its historical PDF-only name; EPUB shares it rather than getting its own — see `BookImportFormat`, documented under `PDFImportModels.swift` above, on why this and `PDFImportManager` weren't renamed): Home reserves an appended shelf slot immediately, the security-scoped pick is copied to `source.pdf`/`source.epub` (`job.resolvedFormat.sourceFileExtension`), and bounded `cover.jpg` artwork is produced before text sampling — rendered from physical page 1 for a PDF, re-encoded from the OPF's declared cover image for an EPUB. Until the cover is ready the fixed slot shows a light matrix loader. For a PDF, every extracted physical page is atomically checkpointed under `pages/` (EPUB parsing is cheap enough next to writing page files that it has no equivalent raw checkpoint and simply re-parses, deterministically, on a resume); finalized `ReaderPage` bodies are written individually under `reader-pages/` either way, and `jobs.json` records phase/page progress, monotonic aggregate progress, and shelf order. The job UUID becomes the final project UUID, so its lifted/dimmed cover settles into the same slot without completion reflow. Failed slots retain inline Retry/Delete and active slots can be cancelled. Finalization pre-renders versioned `spine-artwork-v1.png` from the cover at the page-count-derived shelf width, and — EPUB only — writes an optional `chapters.json`; Library copies all of this beside the completed project's pages, so rendering never depends on the retained job directory. `PDFImportManager` restores unfinished jobs at launch, gives each run its own processing actor, and uses `beginBackgroundTask` only to checkpoint and submit an opportunistic `BGProcessingTask`; resumption from page files, not uninterrupted work, is the contract. Finalization reads and writes one page at a time. Completion while backgrounded requests a local notification. The copied source/checkpoints remain retained after completion, and there is no fixture/golden-test target yet.

The reader is page-based (`Features/Chapters/` retains its historical folder/type names). Home, Library, completed book imports, and entered text open `ChapterPlayerView` directly on page 1; there is no chapter-*list* route, though an EPUB's chapters are reachable from the page picker (see `ReaderPagePickerSheet`'s own entry). The header shows `Page X of Y`, and themed Previous/Next controls load one page body at a time. Changing pages stops active playback, resets highlighting/auto-scroll/elapsed state, scrolls to the top, and leaves the new page paused. Typed text uses `PageSplitter`'s plain-text entry point (≤2,000 words, paragraph/sentence/word fallback); PDF imports preserve physical pages; EPUB imports page chapter-wise via that same splitter's structured `split(units:)` entry point, one call per book section rather than one for the whole book. Kokoro pages stream — synthesize and play, chunk by chunk, nothing persisted to disk; there is no "Generate" control anymore. Kokoro is the only engine, in the reader and everywhere else. Blank pages show an empty-page message and disable playback. Project metadata and each page body live in separate files under `SavedGenerationsV2`, so opening a 500-page project loads only the current page. Old chapter-based development data is deliberately not migrated. The older on-device streaming/highlighting verification predates this page-navigation refactor; the iOS 17 simulator build is clean, but the new page flow still needs the manual/device checks in the implementation plan. **Not yet built**: `AppCoordinator` and the `Onboarding` feature (no onboarding gate exists — the app opens straight into `RootTabView`, with `SplashView` merely overlaying it for the first couple of seconds of each launch; that is a wordmark, not a gate, and persists nothing).

**Reader page picker:** The floating transport's list button opens `ReaderPagePickerSheet`, whose `LazyVStack` loads/caches only short visible-row previews. For an EPUB, `ChapterPlayerView` loads `library.chapters(for:)` once on appear (it never changes for a project) and hands it to the sheet, which renders top-level chapters as collapsible headers — collapsed by default, the chapter containing the current page auto-expanded — rather than the flat list a PDF (no chapters) still gets. Selecting a page uses the normal page-change path, while each successful change atomically persists the reading position; reopening a project resumes there across relaunches.

**Resume is chunk-level, not page-level.** The bookmark is `(page, chunk)` — see `ReadingPosition` and `SavedGeneration`'s own entries — so reopening a book lands on the chunk playback stopped at rather than the top of its page. `ChapterPlayerView.init` resolves it into `pendingResumeChunk`, which the saved chunk feeds only when the open is *also* deferring to the saved page (a caller naming a page explicitly — the mini player — brings its own live chunk through `ReaderRoute.initialChunkIndex` instead). That one value is consumed by two things and dropped on any page change, so it can never re-apply after the reader has moved on: the read-along's restore-on-mount `.onAppear` scrolls to it through the existing `scrollTarget(forChunk:)` (the same mapping auto-scroll uses, and unanimated, since animating a jump from the page top is a long sweep rather than a restore), and the first Play tap passes it as `startingAtChunk`. Resume is to the chunk's *start*, not an intra-chunk offset — re-hearing at most one sentence is deliberate. Page jumps are deliberately exempt: `jumpToPage` (lock-screen ⏮/⏭) and `promoteNextPage` both start a fresh page at chunk 0. Previous/Next arrows live in the transport header; the old bottom page bar survives only as a fallback when the floating transport is disabled or a page is blank.

**Reader page transitions:** A horizontal swipe across the reader turns the page — left for the next, right for the previous — requiring horizontal dominance over the drag's vertical component plus 60pt of travel, so ordinary vertical scrolling never turns a page. This replaced a 56pt vertical overscroll pull at the physical top/bottom of a page, which needed the overscroll condition precisely because it shared an axis with the read-along's own ScrollView; a sideways drag is not a scroll the view has to be told apart from, so the horizontal gesture needs no scroll-position condition at all and `ReaderScrollMetricsBox`/`ReaderScrollContentReporter` (which existed only to measure pull distance) were removed with it. The header's current page number uses a two-label **vertical** slider — deliberately a different axis from the gesture, so the number climbs as the page count does rather than mirroring the swipe: forward navigation pushes the old number up and out the top with the new one rising in from below, and backward performs the inverse, on a high-damping spring rather than an ease so it settles without a visible stop. The clip is a `LinearGradient` mask, not `.clipped()`, so a travelling number dissolves at the edge instead of meeting a hard line; the fade sits *outside* the 24pt resting box (the view is 34pt tall, and the title row is sized to match so the nav bar can't clip a tail back to a hard edge) because digit ink nearly fills that box at this font, and a fade measured inward from the clip edge would permanently dim the numbers. The completion tick beside the count always occupies its slot, mirrored by equal leading padding, with only its opacity toggling — the title group is centred in the nav bar, so a tick that changed the group's width re-centred and visibly shifted the whole title the moment a page completed. Only the number animates; the page body and the static `Page`/`of N` labels do not.

**Continuous playback and play-from-word:** With "Continue to next page" on (⋯ › Controls, default on), streaming playback advances into the next page by itself and prefetches across the boundary, so the next page's first chunks are ready before the transition — see `BookAudioPlayer`'s entry above for the bounded-lookahead pump that does both. The player publishes the advance via `activeRef`; `ChapterPlayerView` watches that and swaps page content with `loadPage(_:)` alone, while every user-driven page change still goes through `moveToPage(_:)`, which stops playback first. The two are told apart by `currentPageIndex` and `activeRef` disagreeing, which only happens on an automatic advance — a manual change always moves `currentPageIndex` first. Tapping any word (on a playing *or* idle page) selects it and shows a "Play from here" button; only that second tap moves playback, so a mis-tap while reading can't jump position. The tap resolves to an exact word via frames `WordFlowLayout` records during placement, **not** a gesture per word — hundreds of recognisers per page would fight the ScrollView's drag and work against `ParagraphRow`'s whole equality/measurement-cache design. `FlowWordItem.ordinalInChunk` is what makes this work on text that hasn't been synthesized yet: `wordIndexInChunk` is nil until real timings exist, so targeting it alone would silently start at the chunk's beginning — exactly the case tapping ahead is for.

**Reader voice changes:** The floating transport's voice avatar opens the reader's preview-first Voice Library, restricted to the project's persisted engine so changing voices never silently changes the reader engine. Selecting an available voice's `Use Voice` action stops active playback, atomically updates project metadata, and uses the new voice for streaming, avatar artwork, and future reopen — there is no persisted audio to invalidate, since playback is always synthesized on demand. Current voices show a check when usable; a missing pack takes priority with a disabled X badge while selected styling remains. A persistence failure leaves the previous voice selected and shows an error.

**One player, three surfaces:** Read-along, the original-PDF page and the music-style audio view are three branches of `ChapterPlayerView`'s own `readingSurface`, all rendering one `BookAudioPlayer` (`docs/adr/0013-unified-player.md`, superseding 0012's two-engine split). Surface changes use direct contextual buttons rather than a menu: Read Along can open Original Page when a source PDF exists, while Original Page/Audio return to Read Along from the header; the shelf's Listen action and mini player enter Audio. Because they are branches of one view over one player, switching re-renders a branch and never re-runs `.onAppear`, so audio continues at the same position through a toggle. The reader's floating transport is hidden on the audio surface, which carries its own. Two lifecycle rules follow from sharing a player with the mini bar: `.onDisappear` must **not** stop playback (leaving the reader hands off to `MiniPlayerBar`), and `.onAppear` adopts a session already active on its page (`player.isActive(pageRef)` → `loadPage`, not `moveToPage`) instead of restarting it — otherwise opening the reader from the mini player would stop the audio the user just tapped. Entry points choose a surface: the shelf's "Read this" uses the persisted preference, while its headphones button and the mini player both set `ImportHomeView`'s pending surface to `.audio` before pushing.

## Adding a new feature/screen

1. `Sources/Features/<Name>/Views/`, `ViewModels/`, and `Models/` (add `Services/` only if the feature makes its own async/SDK calls).
2. If it needs a push destination within the Main flow, add a case to `Features/TTS/Route.swift`-equivalent (or that flow's own route enum) and a `.navigationDestination` branch — do not introduce a second global router.
3. If it's a new top-level flow (gated, not pushed — like Onboarding), it's switched at the `AppCoordinator`/root level, not inside another flow's `NavigationStack`.
4. Update the target file tree above.

## Code style

- **Keep code comments short.** One line explaining a non-obvious "why," not multi-paragraph essays. Skip it entirely if the code is self-explanatory.
- **Keep commit messages short.** A one-line summary is usually enough; add a couple of plain bullet points only if the change genuinely needs them. No multi-paragraph rationale essays.

## Git & GitHub workflow

- **Non-trivial work (a new feature, not a one-line fix) gets its own branch off `main`**, named for what it does (e.g. `books-first-navigation`), not committed to `main` directly.
- **File a GitHub issue before or alongside starting the work**, then open the PR against `main` referencing it with `Closes #N` in the body — use the `/issue-and-pr` skill (`.claude/skills/issue-and-pr/SKILL.md`) for the mechanical steps rather than running `gh issue create`/`gh pr create` ad hoc.
- **PR body shape**: `## Summary` (bullet points of what changed) + `Closes #N` + `## Test plan` (a manual verification checklist — this app has no automated test suite yet, so be concrete about what to click through).
- Issues use the templates in `.github/ISSUE_TEMPLATE/` (`bug_report.yml`, `feature_request.yml`); blank issues are disabled repo-wide.
- Don't push to `main` or merge a PR as a side effect of other work — those stay explicit, user-requested actions.
