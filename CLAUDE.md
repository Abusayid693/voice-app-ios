# CLAUDE.md

Architecture guide for this repo. Read this before making structural changes to the iOS app at `local-tts/native-ios/`. For *why* things are the way they are (engineering history, decisions, feature status), see `ENG_CONTEXT.md` — this file is the *how to organize new code* reference only.

**Keep the "Target file tree" section below in sync with reality.** Whenever the actual folder structure changes (a Feature added, a Core utility added, a layer introduced), update it in the same commit.

## Project

Standalone native iOS SwiftUI app (no Expo/CocoaPods — see `ENG_CONTEXT.md` for why), Xcode project generated by `xcodegen` from `local-tts/native-ios/project.yml`. Never hand-edit `KokoroAneTest.xcodeproj` — edit `project.yml` and run `xcodegen generate`.

xcodegen detail: `project.yml`'s `sources: [Sources]` is a whole-folder reference — xcodegen recurses automatically, so new subfolders under `Sources/` need **no** `project.yml` edit, only `xcodegen generate` re-run before building. Exception: `Info.plist`'s path is referenced explicitly via `info.path:` and must be updated if it moves.

## Architecture: MVVM + Services, feature-first folders

Views bind to a ViewModel; ViewModels own `@Published` UI state and orchestrate; Services own the actual async SDK/engine calls. Views never call an SDK directly; ViewModels never call `AVAudioEngine`/FluidAudio directly.

- **View** — SwiftUI only, no business logic. `@ObservedObject`/`@StateObject var viewModel: ...`, bindings like `$viewModel.text`.
- **ViewModel** — `@MainActor final class ...: ObservableObject`. Owns `@Published` state, calls into Services, translates results into UI state. Never touches FluidAudio or AVFoundation types directly.
- **Service** — owns the actual async SDK calls (FluidAudio managers, `AVAudioEngine`/`AVAudioPlayerNode`, HTTP calls). Reports progress via callback closures passed in by the ViewModel, not via its own `@Published` state — all `@Published` state lives on the ViewModel only.
- **Model** — plain data/enums, no logic.
- **Core/** — cross-feature utilities with no feature-specific meaning (e.g. a generic HTTP/JSON helper used by more than one feature's Service).
- **`Shared/`, `DesignSystem/`** — not created yet. Add only when a real second consumer exists; do not pre-scaffold empty folders for hypothetical future needs.

## Adding a new feature/screen

1. `Sources/Features/<Name>/Views/`, `ViewModels/`, and `Models/` (add `Services/` only if the feature makes its own async/SDK calls).
2. If it needs a push destination within the Main flow, add a case to `Features/TTS/Route.swift`-equivalent (or that flow's own route enum) and a `.navigationDestination` branch — do not introduce a second global router.
3. If it's a new top-level flow (gated, not pushed — like Onboarding), it's switched at the `AppCoordinator`/root level, not inside another flow's `NavigationStack`.
4. Update the target file tree above.
