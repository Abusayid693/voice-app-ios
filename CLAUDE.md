# CLAUDE.md

Architecture guide for this repo. Read this before making structural changes to the iOS app at `local-tts/native-ios/`. For *why* things are the way they are, see `docs/adr/` (one file per decision) and `CHANGELOG.md` (what shipped, by version) — this file is the *how to organize new code* reference only.

**Keep the "Target file tree" section below in sync with reality.** Whenever the actual folder structure changes (a Feature added, a Core utility added, a layer introduced), update it in the same commit.

## Project

Standalone native iOS SwiftUI app (no Expo/CocoaPods — see `docs/adr/0001-standalone-native-prototype.md` for why), Xcode project generated by `xcodegen` from `local-tts/native-ios/project.yml`. Never hand-edit `KokoroAneTest.xcodeproj` — edit `project.yml` and run `xcodegen generate`.

xcodegen detail: `project.yml`'s `sources: [Sources]` is a whole-folder reference — xcodegen recurses automatically, so new subfolders under `Sources/` need **no** `project.yml` edit, only `xcodegen generate` re-run before building. Exception: `Info.plist`'s path is referenced explicitly via `info.path:` and must be updated if it moves.

**Before every commit that touches `Sources/`, `project.yml`, or adds a bundled resource folder**: run `xcodegen generate`, then check `DEVELOPMENT_TEAM` in the regenerated `KokoroAneTest.xcodeproj/project.pbxproj` still matches `project.yml`'s `DEVELOPMENT_TEAM` (`grep -n DEVELOPMENT_TEAM KokoroAneTest.xcodeproj/project.pbxproj`). Xcode's automatic signing has silently rewritten this to a different team mid-session more than once, and once leaked into a `main` merge — catching it before committing avoids shipping a stale/wrong signing team in the generated project file. A new SwiftPM package dependency is exactly as fragile if added by hand-editing `project.pbxproj` instead of `project.yml`'s `packages:`/target `dependencies:` — happened once with `Hugeicons` (below), and reproduced directly: regenerating from the `project.yml` as it stood on disk silently deleted the hand-added dependency, which would have broken the next person's build with no warning.

Three icon packages are in play right now, mid-migration, not a mistake to consolidate reflexively: SF Symbols (system look, e.g. Settings/Storage rows), `LucideSwift` (this app's default non-system icon set, most call sites), and `Hugeicons` (`https://github.com/iSapozhnik/hugeicons-swift`, pinned by `revision:` — no tagged release as of this pin) — replacing Lucide in a growing but incomplete set of call sites (`RootTabView`'s tab icons, `CreateYourOwnRow`, `GenerationRow`, `PreviewVoiceCard`, `ImportHomeView`'s Projects-row icon, `ChapterPlayerView`'s play/pause). Check which a given file already uses before adding a new icon to it rather than assuming — some files (`CustomTabBar`'s "+" button, most of `ChapterPlayerView`) still deliberately mix both.

## Architecture: MVVM + Services, feature-first folders

Views bind to a ViewModel; ViewModels own `@Published` UI state and orchestrate; Services own the actual async SDK/engine calls. Views never call an SDK directly; ViewModels never call `AVAudioEngine`/FluidAudio directly.

- **View** — SwiftUI only, no business logic. `@ObservedObject`/`@StateObject var viewModel: ...`, bindings like `$viewModel.text`.
- **ViewModel** — `@MainActor final class ...: ObservableObject`. Owns `@Published` state, calls into Services, translates results into UI state. Never touches FluidAudio or AVFoundation types directly.
- **Service** — owns the actual async SDK calls (FluidAudio managers, `AVAudioEngine`/`AVAudioPlayerNode`, HTTP calls). Reports progress via callback closures passed in by the ViewModel, not via its own `@Published` state — all `@Published` state lives on the ViewModel only.
- **Model** — plain data/enums, no logic.
- **Core/** — cross-feature utilities with no feature-specific meaning (e.g. a generic HTTP/JSON helper used by more than one feature's Service).
- **`DesignSystem/`** — cross-feature UI tokens (currently just the Import screens' fixed dark color palette). **`Shared/`** — not created yet; add only when a real second consumer exists, same as everything else here.

**One ObservableObject per concern — object granularity *is* re-render granularity.** `objectWillChange` carries no information about *which* property changed, so every `@Published` write re-renders every view observing that object. Two concrete bugs came from ignoring this while everything lived on `TTSViewModel`: the preview metering loop (~15 writes/sec) re-rendered Import's whole 70-tile Trending scroll for the length of every preview, and pack-download progress re-rendered every screen that merely reads pack readiness. Both were fixed by splitting the state onto its own object (`VoicePreviewPlayer`, `VoicePackStore`), not by memoizing views. Two rules follow: when adding state to a ViewModel, ask whether it changes at a different *rate* than what's already there — if so it wants its own object; and a view must not subscribe to an object it never reads. That second rule is now enforced structurally by `App/AppEnvironment.swift`: objects a view only hands onward arrive bundled in that one plain, non-observable container (held as an ordinary `let`, so it subscribes to nothing), while objects a view genuinely observes are passed to it explicitly as `@ObservedObject` parameters. Deliberately **not** `@EnvironmentObject`, which has no non-subscribing read and would re-render every view that merely touches an object — nor a custom `EnvironmentKey`, for the reason in that file's tree entry above. This also caught two real cases: `ImportHomeView` was observing `VoiceCloneViewModel` and `LibraryTabView` was observing `TTSViewModel`, both only to forward them. Note nested `ObservableObject` changes do **not** reach a parent's `objectWillChange` — that's why views reach the store as `viewModel.packs` and observe it directly, rather than through a forwarding property on `TTSViewModel`.

**Voice metadata belongs in `VoiceCatalog`, nowhere else.** Anything describing a voice — display copy, avatar, persona tagline, preview line, locale — goes on `Voice` and into that catalog. It used to live as five sparse dictionaries plus two divergent prefix parsers spread across a View file and a ViewModel, which meant adding one language touched six files and shipped a bug from a missed spot. Don't reintroduce a per-voice lookup table next to the code that consumes it; add a field to `Voice` instead. Same rule for the code-prefix convention (`af_`/`bf_`/`zf_`/`jf_`): `VoiceCode` is the only place that parses it.

        ChapterPlayerView.swift    // DONE — the music-player screen for a chapter, reachable both from a saved chapter and from Play on one that's only streaming (`ChaptersListView`) — the whole page is read-along text. Highlighting is word-level for English Kokoro chunks in either mode; a chunk with no word timings (non-English voice, a manifest saved before this feature, or — streaming — a chunk not yet synthesized) falls back to whole-chunk-only granularity. Rows are **paragraphs, not synthesis chunks**: `computeChunkGaps`/`computeParagraphGroups` locate each ~350-char synthesis chunk as a literal substring of the chapter's own text and group consecutive chunks with no real newline between them, so a paragraph the chunker had to cut for its length budget still renders as one continuous flow instead of breaking mid-line at the cut. **A paragraph's newline is usually not between two chunks — it's inside one**, because `KokoroTextChunker` trims chunks with `.trimmingCharacters(in: .whitespaces)` and `CharacterSet.whitespaces` is Unicode Zs + tab, which excludes newline; chunk ranges are also contiguous, so the gap between two consecutive matches is normally empty. Break detection therefore checks three places, not one (the gap between matches, the previous chunk's trailing newline, this chunk's leading newline), and `wordItems` carries a chunk's *trailing* newlines onto the next chunk's first word — `splitPreservingSeparators` only reports whitespace that *precedes* a word, so a chunk ending in `"\n\n"` has nothing to attach them to and would otherwise drop the break entirely. Checking only the inter-match gap reported "no break" at every boundary, which merged whole chapters into one paragraph group. Each row is built by `WordFlowLayout` (`DesignSystem/WordFlowLayout.swift`), not concatenated `Text` — per-word background highlighting needs each word to be its own styleable view, which `Text + Text` can't do; every word carries constant padding regardless of highlight state, and a paragraph's construction never changes based on playback state (only which word's background is filled) — the "construction must stay fixed" rule from an earlier pause/resume reflow bug. **Read-along scroll-jank fix**, the reason for most of the state here: precomputed `paragraphWordItems`/`paragraphRevisions` (one revision *per paragraph*, not a shared counter — a streaming chunk arrival changes exactly one paragraph's words) feed `ParagraphRow: View, Equatable`, whose `==` compares only scalars/small enums so SwiftUI can skip re-running a paragraph's `body` entirely when nothing changed — without this, `chapterPlayer`'s 4Hz ticker rebuilt every paragraph's full word list on every publish regardless. `recomputeWordItems` does the one O(words) comparison (`FlowWordItem: Equatable`) that decides which revisions to bump, once per chunk arrival, never inside `ParagraphRow.==` itself. **Revisions come from one monotonic counter (`revisionCounter`) and are never reset or reused** — since `==` deliberately doesn't compare `items`, a revision's only job is to differ from the value a row last rendered with, and per-row counters restarting at 0 (what a group-count change used to do) could hand a row the same revision alongside completely different content: `==` then reported equal, SwiftUI skipped the body, and the row rendered *stale* text until some unrelated compared field changed. That was a real bug — a paragraph rendered correctly, then visibly collapsed and reflowed the moment playback reached it, because flipping `isCurrentGroup` was the unrelated change that finally forced a rebuild. Relatedly, a row is the **same view type whether or not it's the playing one**: `TimelineView` wraps every row (only the tick interval varies, 0.08s vs effectively never) rather than sitting inside an `if`, since an `if`/`else` between a wrapped and unwrapped row changes its structural identity, tearing it down and re-measuring it — and everything below it in the `LazyVStack` — each time the highlight entered or left. `groupHeightsBox`/`ScrollActivity` are reference-type boxes in `@State`, not `@State` values directly — mutating a class property doesn't invalidate the view the way reassigning a `@State` value does, which matters since tap-height measurement fires on every layout pass and drag events fire at display rate. **Auto-scroll** pauses on any manual scroll (`isAutoScrollPaused`), resumes only when the user taps the floating "jump to current word" pill, not a timer — `ReaderScrollVisibilityObserver` (`.onScrollVisibilityChange` on iOS 18+, `LazyVStack` onAppear/onDisappear as the iOS 17 fallback — the read-along uses `LazyVStack` specifically so that fallback's timing correlates with real scroll visibility) tracks which paragraph is on-screen so the pill only shows when the playing paragraph is genuinely scrolled off. A multi-chunk paragraph auto-scrolls to a progress-anchored point matching the playing chunk's own position within it, not always centered. Tap-to-seek estimates a target chunk from where within a merged paragraph the tap landed (character-length-weighted, via `SpatialTapGesture` + a `GeometryReader`-measured row height). **Floating player** collapses to a small pill (`isPlayerCollapsed`) or expands to the full transport bar, `matchedGeometryEffect`-animated between the two, Liquid Glass on iOS 26+ (tinted with the active `ReaderTheme`) or a themed translucent-material fallback below that. Play/pause bounces (`animatePlayPauseIcon`): scale down, swap the icon at the compressed midpoint so the two never cross-fade, spring back — skipped under Reduce Motion, its `Task` cancelled both by a new toggle interrupting a running one and on `.onDisappear`; still separately pulses opacity while `chapterPlayer.isBuffering`. **PDF import (text-layer v1):** Both PDF upload actions use Apple's PDFKit entirely on-device; no third-party extractor, server upload, or OCR is involved. Embedded images are ignored for reading, while a small rendered image of physical page 1 becomes the optional project cover. A PDF whose distributed sample pages contain no selectable text is rejected with the scanned-PDF message. `PDFKitTextExtractor` reconstructs a best-effort reading order from line geometry rather than trusting `PDFPage.string`: it normalizes page rotation/crop coordinates, treats wide lines as bands, clusters the remaining lines by horizontal start to infer columns, and reverses column order for predominantly RTL text. This works for conventional single-/multi-column pages but tables, overlapping callouts, vertical writing, and unusual magazine layouts remain best effort.

PDF imports are page-preserving: every physical PDF page produces exactly one `ReaderPage` with the same zero-based index, and blank physical pages remain present as empty reader pages. Bookmarks, outlines, headings, and document word count never create or merge pages. Repeated top/bottom lines are removed when their normalized signature occurs on at least 35% of pages, printed page-number-only lines are removed in those bands, and a trailing hyphen is removed only before a lowercase continuation. V1 rejects locked PDFs, requires at least 500 extracted alphanumeric characters across the completed document, and has no manual-review step.

Imports are durable jobs under `Application Support/PDFImports/<job-id>`: the security-scoped pick is copied immediately to `source.pdf`, a bounded `cover.jpg` is rendered from physical page 1, every extracted physical page is atomically checkpointed under `pages/`, finalized `ReaderPage` bodies are written individually under `reader-pages/`, and `jobs.json` records phase/page progress. On finalization the cover is copied beside the completed project's pages, so Projects/Library do not depend on the import job directory. `PDFImportManager` restores unfinished jobs at launch, gives each run its own `PDFProcessingActor` so PDFKit access stays serialized, and uses `beginBackgroundTask` only to checkpoint and submit an opportunistic `BGProcessingTask`; iOS may interrupt that task, so resumption from page files is the contract. Finalization reads and writes one page at a time rather than collecting the whole document. Completion while backgrounded requests a local notification; foreground completion appears in Home/Library. Failed jobs remain visible with Retry/Delete, active jobs can be cancelled, and completed/cancelled cards disappear from Home. The copied source/checkpoints are currently retained after completion, with no completed-job cleanup UI yet. PDF import still needs an end-to-end device/500+ page verification pass, and there is no fixture/golden-test target yet.

The reader is page-based (`Features/Chapters/` retains its historical folder/type names). Home, Library, completed PDF imports, and entered text open `ChapterPlayerView` directly on page 1; there is no chapter-list route. The header shows `Page X of Y`, and themed Previous/Next controls load one page body at a time. Changing pages stops Kokoro/Pocket/Supertonic playback, cancels only active streaming playback, resets highlighting/auto-scroll/elapsed state, scrolls to the top, and leaves the new page paused; background Kokoro Generate jobs continue. Typed text uses `PageSplitter` (≤2,000 words, paragraph/sentence/word fallback), while PDF imports preserve physical pages. Kokoro pages can stream or generate one merged WAV + timing manifest per page; the header owns Generate/progress/cancel for the current page. Pocket and Supertonic use the saved project's engine and voice through `TTSViewModel.speakPage`, expose only supported play/stop behavior, and do not show seek/timing controls. Blank pages show an empty-page message and disable playback/generation. Project metadata and each page body live in separate files under `SavedGenerationsV2`, so opening a 500-page project loads only the current page. Old chapter-based development data is deliberately not migrated. The older on-device streaming/highlighting verification predates this page-navigation refactor; the iOS 17 simulator build is clean, but the new page flow still needs the manual/device checks in the implementation plan. **Not yet built**: `AppCoordinator` and the `Onboarding` feature (no onboarding gate exists — the app opens straight into `RootTabView`).

**Reader page picker:** The compact progressive-blur bottom bar holds the leading Pages action and trailing 40pt Previous/Next icon buttons. Pages opens `ReaderPagePickerSheet`, whose `LazyVStack` loads/caches only short visible-row previews. Selecting a page uses the normal page-change path, while each successful change atomically persists `lastReadPageIndex`; reopening a project resumes there across relaunches. Generate intentionally remains in the reader header.

**Reader page transitions:** At the physical top or bottom of a reader page, a deliberate 56pt overscroll pull turns to the previous or next page; ordinary fast scrolling does not. The header's current page number uses a clipped two-label vertical slider: forward navigation pushes the old number upward with the new number entering from below, and backward navigation performs the inverse. Only the number animates; the page body and the static `Page`/`of N` labels do not.

**Reader voice changes:** The expanded player's voice avatar opens the same `VoiceSettingsSheet` used by Write Text, restricted to the project's persisted engine so changing voices never silently changes the reader engine. Selecting another available voice stops active playback, cancels that project's Kokoro Generate jobs, removes all saved/staged audio made with the previous voice, atomically updates project metadata, and uses the new voice for streaming, generation, avatar artwork, and future reopen. Selecting the already-active voice is a no-op; unavailable packs remain disabled, and a persistence failure leaves the previous voice selected and shows an error.

## Adding a new feature/screen

1. `Sources/Features/<Name>/Views/`, `ViewModels/`, and `Models/` (add `Services/` only if the feature makes its own async/SDK calls).
2. If it needs a push destination within the Main flow, add a case to `Features/TTS/Route.swift`-equivalent (or that flow's own route enum) and a `.navigationDestination` branch — do not introduce a second global router.
3. If it's a new top-level flow (gated, not pushed — like Onboarding), it's switched at the `AppCoordinator`/root level, not inside another flow's `NavigationStack`.
4. Update the target file tree above.

## Code style

- **Keep code comments short.** One line explaining a non-obvious "why," not multi-paragraph essays. Skip it entirely if the code is self-explanatory.
- **Keep commit messages short.** A one-line summary is usually enough; add a couple of plain bullet points only if the change genuinely needs them. No multi-paragraph rationale essays.

## Git & GitHub workflow

- **Non-trivial work (a new feature, not a one-line fix) gets its own branch off `main`**, named for what it does (e.g. `voice-cloning-pocket-tts`), not committed to `main` directly.
- **File a GitHub issue before or alongside starting the work**, then open the PR against `main` referencing it with `Closes #N` in the body — use the `/issue-and-pr` skill (`.claude/skills/issue-and-pr/SKILL.md`) for the mechanical steps rather than running `gh issue create`/`gh pr create` ad hoc.
- **PR body shape**: `## Summary` (bullet points of what changed) + `Closes #N` + `## Test plan` (a manual verification checklist — this app has no automated test suite yet, so be concrete about what to click through).
- Issues use the templates in `.github/ISSUE_TEMPLATE/` (`bug_report.yml`, `feature_request.yml`); blank issues are disabled repo-wide.
- Don't push to `main` or merge a PR as a side effect of other work — those stay explicit, user-requested actions.
