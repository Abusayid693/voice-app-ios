# ENG_CONTEXT.md

Engineering context for this repo — what the app does, why it exists, and every non-obvious decision made so far. Read this at the start of a new session to understand the app without re-deriving everything from git history. **Keep this updated** whenever a feature, decision, or constraint changes — add to it, don't let it drift from reality.

For *how to organize new code*, see `CLAUDE.md` instead (architecture conventions + target file tree).

## What this app is

A standalone native iOS validation harness (`local-tts/native-ios/`, xcodegen-generated Xcode project — no Expo, no CocoaPods, deliberately separate from any other app) for testing two on-device TTS engines from [FluidInference/FluidAudio](https://github.com/FluidInference/FluidAudio)'s Swift SDK, on real hardware. Origin: a separate Expo app ("Voicenote") needs real, on-device TTS; wiring FluidAudio's Swift Package into that Expo/CocoaPods build is a real, risky change (`useFrameworks: dynamic`). This app exists to de-risk that decision first — confirm the engines actually work well, how big the downloads are, how fast synthesis is, and what the real constraints are — before touching the Expo app's working CPU TTS path at all. See `plan.md` at repo root for the original planning doc.

Signing: `project.yml` specifies Apple Development team `Q2F3H94YUP`, but the committed `.xcodeproj` currently has `V667L4VT6C` (Xcode changed this outside of any session, likely via automatic signing when opened directly in Xcode) — these are **out of sync**. Since `xcodegen generate` regenerates the `.xcodeproj` from `project.yml`, running it again will silently revert the team back to `Q2F3H94YUP`. Reconcile these (update `project.yml` to match whichever team actually works) before the next regenerate, or the signing will break again. Bundle id `com.rehanchoudhury.kokoroanetest`. iOS 17 deployment target, Swift 5.0.

## The two engines

### Kokoro-ANE (`KokoroAneManager`)
7-stage CoreML chain (Albert→PostAlbert→Alignment→Prosody→Noise→Vocoder→Tail). FluidAudio's own hosted HF repo only publishes one voice per language (`af_heart` English / `zf_001` Mandarin) — their docs call this a hard model-conversion constraint. **We confirmed that's not actually true at the architecture level**: every one of the 7 stages is voice-agnostic. `Albert`, `Alignment`, and `Tail` never touch voice data at all; `PostAlbert`/`Prosody` take `style_s` and `Noise`/`Vocoder` take `style_timbre` as plain runtime tensor inputs, not anything baked into compiled weights. This app ships a custom-bundled model set with every standard Kokoro-82M English voice working as a result — see "Custom Kokoro-ANE model bundle" below for how, and `ENG_CONTEXT.md`'s "voice-agnostic" finding is worth citing if filing the mismatch as a GitHub issue upstream.

Also hard-capped at **≤510 phonemes per call** (Albert's context window), no built-in chunker — the SDK has no autoregressive/streaming path for Kokoro at all (no `synthesizeStreaming()` on `KokoroAneManager`, and architecturally it can't have one: Albert→PostAlbert→Alignment decide the *entire* frame count up front, then the rest runs as one batched pass — there's no point where partial audio exists before the whole thing finishes, unlike PocketTTS's genuinely autoregressive frame-by-frame generation). The app works around both the length cap and the lack of streaming itself — see "Kokoro-ANE chunked, multi-track playback UI" below.

Uses `computeUnits: .default` (unmodified) — an OS-version-aware routing table baked into the SDK to avoid two known bugs (BNNS CPU segfault on iOS 26.4–26.5.x, fixed in 26.6+; GPU RNN JIT assert on macOS 26.5+/M5). Test device is iOS 26.6.1, past the fix line, so no workaround needed.

### Custom Kokoro-ANE model bundle (multi-voice support)

`local-tts/native-ios/CustomKokoroModel/` — **gitignored, ~93MB, fully regeneratable** — holds all 7 real FluidAudio stages (downloaded from `FluidInference/kokoro-82m-coreml`, byte-identical to what the SDK would normally fetch itself), `vocab.json`, and all 28 standard Kokoro-82M English voice `.bin` files (FluidAudio only publishes `af_heart.bin`; the rest are generated directly from the upstream PyTorch checkpoint — no CoreML involved). `DependencyContainer.kokoroManager` points `KokoroAneManager(directory:)` at this bundle instead of the default download location, so `ensureVoicePack` finds every voice already present locally and never touches the network.

**To regenerate the model files** (if the gitignored folder is missing, e.g. on a fresh clone):
```python
from huggingface_hub import snapshot_download
snapshot_download(
    repo_id="FluidInference/kokoro-82m-coreml",
    allow_patterns=[
        "ANE/KokoroAlbert.mlmodelc/*", "ANE/KokoroPostAlbert.mlmodelc/*",
        "ANE/KokoroAlignment.mlmodelc/*", "ANE/KokoroProsody.mlmodelc/*",
        "ANE/KokoroNoise_v2.mlmodelc/*", "ANE/KokoroVocoder.mlmodelc/*",
        "ANE/KokoroTail_v2.mlmodelc/*", "ANE/vocab.json",
    ],
)
```
Note the `_v2` suffixes on Noise/Tail — required exact filenames (`ModelNames.KokoroAne` in FluidAudio's source), and genuine bug fixes (Noise_v2: atan2 phase-correction removing audible high-frequency "sharpness"; Tail_v2: COLA-normalized iSTFT weights — the un-fixed version's raw output is exactly 1.5x too loud). `huggingface_hub` caches via symlinks into a shared blob store — copy with `cp -RL` (dereference) when moving into the project, or the bundled app will ship broken links.

For voice packs, extract directly from the upstream checkpoint (no `convert.py`/CoreML step at all — this is why voice-swapping works with zero model reconversion):
```python
import torch, numpy as np
from huggingface_hub import hf_hub_download
path = hf_hub_download(repo_id="hexgrad/Kokoro-82M", filename=f"voices/{name}.pt")
arr = torch.load(path, map_location="cpu", weights_only=True).numpy().astype(np.float32).reshape(510, 256)
open(f"{name}.bin", "wb").write(arr.tobytes())
```
The 28 English voice names are listed in `TTSViewModel.kokoroVoices`. Drop all of the above (7 `.mlmodelc` dirs + `vocab.json` + `*.bin` files) flat into `CustomKokoroModel/kokoro-82m-coreml/ANE/`.

**Two non-obvious integration details**, both required for this to actually run on-device:
- `project.yml` bundles `CustomKokoroModel/` with an explicit `type: folder` resource entry — this is what makes Xcode copy it as one atomic directory (preserving each `.mlmodelc`'s internal structure) instead of risking it getting flattened by the default source-scanning behavior.
- The installed `.app` bundle is **read-only** at runtime, but CoreML's ANE compilation step needs to *write* analytics/cache data into a model's folder the first time it loads (fails with "You don't have permission to save the file..." otherwise). `DependencyContainer` copies the bundled folder into `Application Support` (writable) once on first launch, and points `KokoroAneManager(directory:)` at that copy, not the bundle directly. Also: locate the bundled folder via `Bundle.main.bundleURL.appendingPathComponent(...)`, not `Bundle.main.url(forResource:withExtension:)` — the latter proved unreliable for this folder reference on-device.

### PocketTTS (`PocketTtsManager`)
Flow-matching LM + Mimi neural codec (autoregressive, per-80ms-frame generation), fundamentally heavier than Kokoro-ANE (~500MB+ vs ~166MB download) but **genuinely multi-voice**: 26 real published voices (`alba`, `anna`, `michael`, `george`, etc. — literary character names from `kyutai/pocket-tts`, mostly unrelated to Kokoro's `af_`/`am_`/`bf_`/`bm_` naming despite two name collisions with Kokoro voices, `michael`/`george`, which are *different* voices). Verified all 26 exist as real `.safetensors` files in `constants_bin/` on HF (not just docs) before adding them to the picker.

**Placement chosen deliberately: `.ane`, not the SDK's default `.gpu`.** The SDK's `.gpu` default is benchmarked/justified with Mac-specific numbers (M-series GPU vs ANE per-call latency); its own doc for `.ane` explicitly mentions "iOS placement" as a reason to use it. Since this app's whole purpose is validating the ANE path on iPhone, `.ane` was chosen over the library default. Consequence: `precision: .int8` has **no effect** under `.ane` placement (only `.gpu`'s FlowLM variant is quantizable) — download is ~503MB fp16, not the ~433MB int8+gpu figure that appeared in early testing before this was corrected.

Voice accent: **unconfirmed**. No dialect metadata found in docs or accessible source; upstream `kyutai/pocket-tts` model card is gated. Don't assume "American English" without checking on-device.

Playback: **streaming**, not buffered — `synthesizeStreaming()` yields 80ms `AudioFrame`s (chunked internally at ≤50 tokens/chunk, sentence→clause→word boundaries) fed incrementally into `AVAudioEngine`/`AVAudioPlayerNode` as they're generated, instead of assembling one WAV first. Exposes "time to first audio" and chunk-progress metrics in the UI.

**Known unresolved issue**: a small audible glitch/overlap at chunk boundaries within one long synthesis (the KV cache resets per chunk internally in the SDK). A fix was attempted (insert ~300ms silence buffer at each chunk boundary) and **explicitly reverted** at the user's request — do not re-attempt this exact approach without new direction; it works mechanically (verified building) but was undone before being kept. If revisiting, reconsider a smaller gap value and/or a crossfade instead of hard silence.

## Kokoro-ANE chunked, multi-track playback UI

Kokoro's 510-phoneme cap and lack of any streaming path (see above) meant long text either errored or you had to wait for the whole thing to synthesize before hearing anything. `Features/TTS/Models/KokoroTextChunker.swift` splits text on sentence boundaries (falling back to word boundaries for one very long sentence) at a conservative ~350-character budget (phoneme count isn't knowable without running G2P, so this is a character-count stand-in with headroom).

**Each "Generate" tap creates an independent track**, not one shared continuous stream — `KokoroGeneration` (`Features/TTS/Models/KokoroGeneration.swift`) holds one generation's sub-chunks, audio, and per-chunk state; `TTSViewModel.kokoroGenerations: [KokoroGeneration]` is append-only, like a playlist. `Features/TTS/Views/KokoroGenerationListView.swift` renders one row per track — its own play/pause/buffering button, a segmented bar for its own sub-chunk progress (blue = playing, light blue = generated, light grey = waiting, red = failed), and any error inline. Only one track plays at a time — selecting a different one stops whatever was active and starts the new one from its beginning, like switching songs; a track never auto-advances into a different track when it ends.

Generation itself is one persistent background worker (`ensureKokoroGenerationRunning()`) shared across all tracks — each iteration scans every track in creation order for its next `.waiting` chunk and synthesizes it, so a Generate tap while the worker is already running just adds more work to the same loop rather than needing a restart. A chunk that fails to synthesize is marked `.failed` (not left `.waiting` forever) with the error message attached to its track, and the worker moves on to the next chunk instead of dying — one bad chunk doesn't block or hang the rest of the queue.

Playback uses one `AVAudioPlayer` per chunk (not the `AVAudioEngine`/`AVAudioPlayerNode` PocketTTS uses) — `AVAudioPlayer.pause()`/`.play()` natively support pausing and resuming mid-chunk; a small `NSObject`-conforming delegate (`KokoroChunkPlaybackDelegate`) bridges `audioPlayerDidFinishPlaying` to advance to the next chunk within the active track.

**Bug already found and fixed once**: an earlier version conflated "start playback" with "regenerate" — tapping Play both decided whether to resume vs. restart *and* triggered generation, gated only on whether the chunk list was non-empty. That flag never got cleared after a run finished or when the text changed, so playing new text after finishing old text just replayed the stale, already-finished `AVAudioPlayer` instead of generating anything new. The Generate/Play split above is the fix — don't reintroduce a single combined "smart" button that tries to infer resume-vs-fresh from state; keep the two actions explicit and separate.

## Pronunciation control / text normalization

Kokoro-ANE: no SSML (`<phoneme>`/`<sub>`/`<say-as>`), no markdown `[word](/ipa/)` overrides — neither exists for `KokoroAneManager`. It does have a real custom-lexicon API (`setEnglishCustomLexicon([String: String])` / `setMandarinCustomLexicon(_:)`), not currently wired into the app. It already normalizes numbers/dates/currency internally before synthesis.

PocketTTS: no built-in number/date/currency normalization — added to the app. `TextNormalizer.shared.tnNormalizeSentence(_:)` (same native NeMo FST engine Kokoro uses internally, exposed here as a public API) runs on the input text in `runPocketTts()` before `synthesizeStreaming()`, so `"$5"` → "five dollars", `"12/12/2024"` → spoken date form, etc. Runs via `Task.detached` since it's a synchronous native call with no `await` — keeps a long input from blocking whichever actor the calling `Task` inherited.

## Download progress UI (both engines)

FluidAudio's own `ProgressHandler`/`DownloadProgress` only reports a fraction (`fractionCompleted: Double`, `phase: .listing/.downloading(completedFiles:totalFiles:)/.compiling`) — **no raw byte totals**. To show "X / Y MB," the app queries HuggingFace's public tree API directly (`https://huggingface.co/api/models/<repo>/tree/main/<path>?recursive=true`) and sums file sizes itself, filtered to just the files the chosen precision/placement config actually downloads (verified against `ModelNames.swift`'s `requiredModels(precision:placement:)` source, not guessed).

Progress-fraction weighting differs by download path (confirmed by reading `ModelHub.swift`): Kokoro's repo-download reserves `0.0–0.5` for download + `0.5–1.0` for a compile phase that never actually fires for these pre-compiled `.mlmodelc` bundles (so the app normalizes by dividing by `0.5`); PocketTTS's subdirectory-download path spans the full `0.0–1.0` (weight `1.0`, no normalization needed). Get this wrong and progress bars either stall at 50% or never reach 100%.

**"Already downloaded" detection is disk-based, not memory-based.** `manager.isAvailable()`-style flags only reflect what's loaded into the current process's RAM, which is always false on a fresh app launch even if the model files are sitting in `Application Support` (persisted, not auto-purged by iOS) from a previous run. The app instead tracks whether a real `.downloading`/`.listing` progress event actually fired (`didDownload`) — only then does it show the download UI or fetch the HF total-size estimate. This makes a warm-cache relaunch skip straight to "Loading models…" instead of showing a fake "Downloading model…".

## Import screen redesign + Setup flow

The app root is now `RootTabView`, a 5-tab `TabView` (Home/Explore/Import/Library/Voices) built to match a consumer-facing mockup the user supplied. Only two tabs have real content: **Home** keeps the original engine/voice debug `Form` screen (`TTSHomeView`, byte-for-byte unchanged) exactly as it was when it was the app's only screen; **Import** (`Features/Import/`, selected by default) is the new redesigned landing page — action grid (Paste a link / Upload a file / Scan text / Write text), a real "Trending voices" row (every Kokoro/Pocket voice, playable — see "Voice previews" below), a real "What's trending" row (live Gutendex book feed, see below), "Create your own book", and a demo "Projects" list. Explore/Library/Voices are `PlaceholderTabView` stand-ins with no real screen yet.

Still deliberately dummy (visually present, no-op on tap, per explicit direction): Paste a link, Upload a file, Scan text, Create your own book, Projects. "What's trending" is a real, paginated Gutendex feed (`GutendexBookService`, `TrendingBooksViewModel`, with a "See all" infinite-scroll screen), not fetched-cover-art demo content.

Only **Write text** is real: it opens `WriteTextView` (full-screen `TextEditor`, floating Generate + Settings buttons), which is functionally Import's counterpart to `TTSHomeView`'s existing `TextEntrySheet` but intentionally a separate file — the layouts diverge enough (floating bottom bar + inline progress vs. top toolbar) that evolving `TextEntrySheet` in place would have meant branching its behavior by caller. `TextEntrySheet` still backs the Home tab's own flow unchanged. Generate stays on `WriteTextView` and shows progress inline (reuses `KokoroGenerationListView` for Kokoro; a small status card bound to the same `@Published` fields for PocketTTS) rather than navigating away — the user was explicit that Generate should not pop back to Import.

**Setup flow**: a "Setup" button on Import always opens `SetupSheet`, showing the two voice packs (`VoicePack.kokoro` / `.pocket`) as either a checkmark ("already downloaded") or a "Download" button with progress — never hidden, per the user's clarified answer ("keep button, show as already-set-up" rather than hiding it once done). The two packs are fundamentally asymmetric:
- **Kokoro** is bundled at build time (`CustomKokoroModel/`, see above) and copied into `Application Support` synchronously in `DependencyContainer.init()`, before any UI shows — so `TTSViewModel.isKokoroPackReady` is true for virtually every launch the instant the ViewModel exists. `downloadKokoroPackIfNeeded()` only does real work in the rare case that bundle copy failed.
- **PocketTTS** has no bundled fallback — it's a genuine ~500MB network download the user opts into. There's no cheap, disk-based "is this already downloaded" check exposed by the SDK (`manager.isAvailable()` is RAM-based, always false on a fresh launch even with files on disk — see "Download progress UI" above), so `TTSViewModel.isPocketPackDownloaded` is a persisted `UserDefaults` flag set the first time `downloadPocketPackIfNeeded()` succeeds, and read back at `init`.

**Bug found and fixed while wiring this up**: `KokoroEngineService.ensureModels()` was calling `KokoroAneResourceDownloader.ensureModels(variant:progressHandler:)` with no `directory:` override, so it checked/downloaded into FluidAudio's *default* cache path (`Application Support/fluidaudio/Models/...`) — a completely different directory from the one `DependencyContainer.kokoroManager` actually reads from (`Application Support/CustomKokoroModel`, via the bundled-copy mechanism above). `manager.initialize()`'s own internal `ensureModels` call already passed the right directory, so this only mattered for the standalone pre-check `ensureKokoroGenerationRunning()`/Setup call ever did — but on a genuinely fresh install it could have triggered a real, unnecessary ~93MB network download of the stock FluidAudio repo for a pack that was already fully bundled. `DependencyContainer` now exposes `kokoroModelDirectory: URL?` alongside `kokoroManager`, and `KokoroEngineService` takes it in its initializer and threads it into `ensureModels(directory:)` — matching what `initialize()` already did internally.

## Voice previews (Trending voices' play button)

Each voice row in Import's "Trending voices" has a play button that plays a short spoken preview of that exact voice. The user chose **pre-recorded clips over live synthesis at tap time** — there's no external source of "54 voice actors," the only source of these voices is this app's own on-device engines, so the clips are generated once (using the app's real synthesis, exactly like any other generation) and bundled, rather than synthesized live on every tap. This mirrors the `CustomKokoroModel/` bundle above: a one-time generation step produces files that get committed, not something done live at runtime.

**Per-voice lines, not one shared sentence**: `Features/Import/Models/VoicePreviewLines.swift` holds a distinct, natural-sounding 16-20 word sentence per voice code (varied phrasing/topics, deliberately not "Hello, this is a preview" repeated 54 times) so voices are easy to tell apart when auditioned back to back, plus one `fallback` sentence for any voice missing an entry.

**Shipped runtime side is pure file playback, no engine involved**: `TTSViewModel.togglePreview(voiceName:engine:)` resolves `Bundle.main.url(forResource: voiceName, withExtension: "wav", subdirectory: "VoicePreviews/Kokoro"` (or `.../Pocket`)`)` and plays it with a dedicated `AVAudioPlayer` (`previewPlayer`, its own delegate — deliberately never shares state with `kokoroPlayer`/`pocketService`'s engine). If a voice's clip isn't bundled, it's a silent no-op — same as tapping any other row that isn't wired up yet. This is why previewing never collides with an in-progress "Write text" generation and has no first-tap synthesis latency, unlike live synthesis would have.

All 28 Kokoro clips are captured and bundled at `local-tts/native-ios/VoicePreviews/Kokoro/<voice>.wav`. The raw exports also live at `local-tts/native-ios/assets/kokoro-previews/` (same pattern as `assets/voice-covers/` for the cover images) as the source-of-truth copy.

**Bug found and fixed while wiring this up — same lesson as `CustomKokoroModel` above**: these were first added under `Sources/Resources/VoicePreviews/Kokoro/`, relying on `project.yml`'s plain whole-folder `sources: [Sources]` scan. That flattens loose files (subdirectory nesting is Xcode-navigator-only organization, not preserved in the built app bundle) — so at runtime `Bundle.main.url(forResource:withExtension:subdirectory: "VoicePreviews/Kokoro")` always returned `nil`, and `togglePreview` silently no-op'd (by design, treating a missing clip like "not available") — the play button visibly did nothing. Fixed by moving the folder to a top-level `VoicePreviews/` (sibling to `Sources/`, matching where `CustomKokoroModel/` already lives) and giving it its own `type: folder` entry in `project.yml`, exactly like `CustomKokoroModel` — that's what actually makes Xcode copy it as one atomic directory with its internal structure intact.

**Regeneration recipe** (redo this if the preview line ever changes, or to add Pocket's clips): the capture tooling was temporary and has been removed from the shipped app (it lived as `TTSViewModel.generateKokoroPreviewClips()` + a "Voice Previews (dev)" section on the Home tab, `TTSHomeView`) — to redo it, re-add a debug button that loops the voices, synthesizes each one's `VoicePreviewLines` line via `kokoroService.synthesize(text:voice:)` (Kokoro's one-shot WAV `Data`), writes each to `<Documents>/VoicePreviews/<voice>.wav`, and offers them via a `ShareLink(items:)` to export off-device (Save to Files, AirDrop, etc.); copy the result into `VoicePreviews/Kokoro/` at the project root (not under `Sources/` — see the bug above), then remove the debug tooling again. Pocket's 26 voices need the same pattern but accumulating `synthesizeStreaming`'s 80ms frames into one buffer via `AVAudioFile` instead of a one-shot call (Pocket has no one-shot synthesize) — not yet done as of this writing, so Pocket voices' play buttons are still a no-op.

## Voice cloning (`Features/VoiceClone/`)

Users can record a short sample of their own voice and get a reusable PocketTTS voice back — this is **Pocket-only** (Kokoro-ANE has no cloning capability) and rides entirely on APIs already present in the exact FluidAudio version this app is pinned to (`v0.15.6` — confirmed via `Package.resolved` before building this, not assumed): `PocketTtsManager.cloneVoice(from:)` runs a sample through Kyutai's Mimi encoder to produce `PocketTtsVoiceData` (a speaker-conditioning embedding), and `synthesize(text:voiceData:)`/`synthesizeStreaming(text:voiceData:)` are parallel overloads of the normal `text:voice:` calls that accept it directly — no upstream SDK gap, no fork needed. `saveClonedVoice`/`loadClonedVoice` persist one as a small binary file. `cloneVoice` itself lazily downloads a separate `mimi_encoder.mlmodelc` model on first call (language-agnostic) — no progress callback exposed for this step, so the UI shows an indeterminate spinner rather than a real progress bar.

**Why its own feature area, not folded into `TTSViewModel`**: recording/cloning/managing a list of user-created voices is a genuinely separate concern from TTS-generation orchestration (which `TTSViewModel` already owns plenty of). `Features/VoiceClone/ViewModels/VoiceCloneViewModel.swift` gets its own `PocketEngineService` instance, constructed from `DependencyContainer` exactly like `TTSViewModel`'s — both safely wrap the same shared `PocketTtsManager` actor/`AVAudioEngine`/`AVAudioPlayerNode`, since `PocketEngineService` holds no state of its own beyond those shared references. `KokoroAneTestApp` constructs one shared `VoiceCloneViewModel` alongside `TTSViewModel` and passes both down through `RootTabView`.

**Where it lives in the UI**: the "Voices" tab (previously an empty `PlaceholderTabView`) is now `VoicesTabView` — list cloned voices, preview them (live synthesis of a short line through `synthesizeStreaming(text:voiceData:)`, since there's no way to pre-bundle a clip for a voice that doesn't exist until cloned — unlike the named-preset previews above), delete them. A second entry point, "Create your own voice" on Import (styled like the existing "Create your own book" row, right below Trending voices), opens the same `RecordVoiceView` directly.

**Recording**: `Features/VoiceClone/Services/VoiceRecorderService.swift` wraps `AVAudioRecorder` (44.1kHz mono 16-bit WAV, capped at 20s — `PocketTtsManager.cloneVoice` accepts 1-30s per FluidAudio's docs, the encoder's fixed input window is effectively ~10s, so the cap just keeps recordings from running away, not a hard model limit) plus `AVAudioPlayer` for preview-before-cloning. Requires `NSMicrophoneUsageDescription` in `project.yml`'s `info.properties` — without it the app crashes on first mic use.

**Importing an existing file** (added alongside recording): `.fileImporter` in `RecordVoiceView` picks any audio file `AVAudioFile` can read; `VoiceRecorderService.importAudioFile(from:)` transcodes it (single-shot `AVAudioConverter`, these clips are short enough to hold entirely in memory rather than streaming the conversion) into the same temp WAV location a recording would use, so everything downstream treats a recording and an import identically.

**Persistence**: cloning is genuinely Pocket-only, but a cloned voice's binary is small and independent of the main Pocket pack — `ClonedVoice` (id, name, createdAt) is the small Codable metadata record, persisted as a UserDefaults+JSON array (same style as `isPocketPackDownloaded`); the actual `PocketTtsVoiceData` binary lives at `ClonedVoice.fileURL` under `Application Support/ClonedVoices/<id>.bin` — both `VoiceCloneViewModel` (writes/deletes) and `TTSViewModel` (reads, to generate with a cloned voice — see below) compute this same path from the one static `ClonedVoice.directory`/`.fileURL`, so neither needs a reference to the other's instance. Both survive app relaunches; only deleting/reinstalling the app clears them.

**Using a cloned voice to generate**: `TTSViewModel.selectedClonedVoice: ClonedVoice?` — when set (and `engine == .pocketTts`), `runPocketTts()` loads its `PocketTtsVoiceData` and calls the `voiceData:` overload instead of `voice:`. `VoiceSettingsSheet` (Write Text's voice picker) gained a "My Voices" section listing `voiceCloneViewModel.clonedVoices`; picking a normal Kokoro/Pocket voice there clears `selectedClonedVoice` back to nil.

**Known upstream limitation** (not a concern for this app today): live cloning is fully reliable for English and the 24-layer non-English packs; best-effort on the smaller 6-layer non-English packs (FluidAudio GitHub issue #793, a confirmed upstream `pocket-tts` architecture constraint) — this app only uses `.english`.

## Settings page (`Features/Settings/`, issue #9)

Reached via a gear icon on Import, presented as a `.sheet` the same way `SetupSheet` is. Originally the gear and the Setup icon shared one `HStack` inside a single toolbar `ToolbarItem`; changed to two separate `ToolbarItem`s so they're genuinely two distinct toolbar controls rather than one grouped item — same visual position, no behavior change.

`SettingsSheet` is just a `List` of three `NavigationLink` rows (Voice Packs / Storage / About) pushing to real content — no more placeholders:

- **`VoicePacksView`**: per-engine downloaded/not status + voice count + real on-disk size for both Kokoro-ANE and Pocket TTS.
- **`StorageView`**: a breakdown (Kokoro pack / Pocket pack / "My voices" cloned-voice count) plus a total, all real sizes.
- **`AboutView`**: app version, read live from the bundle.

**All the size numbers are real, not estimates.** `Core/FileSystem/DiskStorage.swift` (named to avoid colliding with SwiftUI's own `@AppStorage` property wrapper) does the actual measuring: `directorySize(at:)` enumerates a folder recursively and sums `URLResourceValues.fileSize` for every file inside. It's pointed at the three real folders these things already live in, all under `Application Support`:
- Kokoro pack → `viewModel.kokoroModelDirectory` (the writable copy `DependencyContainer` makes of the bundled `CustomKokoroModel/` — see "Custom Kokoro-ANE model bundle" above)
- Pocket pack → `Application Support/fluidaudio/` — not an app-defined path; found by reading FluidAudio SDK source directly (`TTS/Shared/TtsCacheDirectory.swift`), since the SDK owns where it puts downloaded models and exposes no accessor for the path
- Cloned voices → `ClonedVoice.directory` (`Application Support/ClonedVoices/`, same convention voice cloning already uses)

These three don't overlap, so summing them for "Total" on the Storage page is safe.

**Version number**: `AboutView` reads `Bundle.main.infoDictionary?["CFBundleShortVersionString"]` at runtime. The value itself is set in `project.yml`'s `info.properties.CFBundleShortVersionString` (currently `"0.1.0"`), **not** by editing `Sources/Resources/Info.plist` directly — xcodegen fully regenerates that plist from `project.yml`'s `info:` block on every `xcodegen generate`, so a direct edit to the plist gets silently clobbered on the next regenerate. Bumping the version in the future means editing `project.yml`, not the plist.

**Deliberately not covered by Storage/Voice Packs today**: generated audio from "Write text" (`TTSViewModel.kokoroGenerations[].chunkAudio: [Data?]`) lives purely in memory — never written to disk, so it doesn't (and shouldn't yet) appear in the Storage breakdown. Reconcile `project.yml` to the actually-working team, or expect signing to break after every regenerate.
- Kokoro-ANE's 510-phoneme cap is now worked around via app-level chunking (`KokoroTextChunker`) — no longer an open gap, see "Kokoro-ANE chunked, multi-track playback UI" above.
